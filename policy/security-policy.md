# Temper Security Policy: Image Hardening Requirements

Requirements for every image Temper builds and publishes. CI checks the ones
that can be checked mechanically (§5); the rest are met through apko config
review.

Scope: all images in `images/` and the build/sign/scan/publish pipeline in
`.github/workflows/`. `:debug` variants are excluded from production
hardening requirements where noted, and are not published.

## 1. Baseline hardening (all runtime images)

1. **Nonroot by default.** Images run as UID 65532 (the conventional
   nonroot UID). A workload that needs otherwise must justify it in the
   image's own documentation.
2. **No setuid/setgid.** No file in a runtime image may be setuid or setgid,
   whether the bit comes from a package or a recipe.
3. **Read-only-rootfs compatible.** Images must run with a read-only root
   filesystem. Writable state belongs in mounted volumes.
4. **Dropped capabilities.** Containers must drop all capabilities at runtime.
   Images must not rely on capabilities that require elevation.
5. **No package manager in runtime images.** Runtime images contain exactly the
   packages declared in their apko config; no `apk`, no shell outside the
   shell tier (§2), no package database operations at runtime.
6. **Pinned packages.** Every image builds from a committed `apko lock`
   lockfile, so the same inputs reproduce the same package set. Published
   configs never use `latest` package specifiers.
7. **Immutable date tags + digest pinning.** Every release is published under
   a date tag (`YYYY.MM.DD`; a further release the same day is
   `YYYY.MM.DD.1`, `.2`, ...) and is always consumable by pinned digest
   (`repo@sha256:...`). An image with a version line is also tagged
   `<line>-<date>` (`node:26-2026.11.19`). Published tags are never
   rewritten.
8. **Gated `latest`.** `latest` moves to a release only after every image
   in it passes the gates in §5, and only forward: if any image already has
   a newer date tag, `latest` does not move. `latest` is a convenience
   pointer, not a version; pin a digest for reproducible builds. Moving it
   back to an earlier release is a manual, verified step
   (`scripts/rollback-latest.sh`; docs/maintaining.md, "Moving `latest`
   back").
   Line tags (`node:26`, `node:24`) follow the same rules per image and
   line. A repository that publishes two lines has one `latest`, on the
   newer line.

## 2. Distroless default (unless documented)

apko assembles images from exactly the packages selected, so distroless is
the default shape, not an add-on. This is what satisfies §1.3 and §1.5. The
shell tier is the only set of images that intentionally includes a shell:

- `base-shell` and the `:debug` variants, for troubleshooting only.
- The builder images (`base-glibc-dev`, `go-builder`, `node-builder`), for
  build stages only.

None of them is a production runtime base image.

## 3. Supply chain

1. **Pinned inputs.** Image builds install packages from committed apko
   lockfiles that pin each version and checksum. Package builds (melange)
   install a pinned build environment and fetch nothing while building: the
   gofips Go build runs with `GOPROXY=off`, `GOTOOLCHAIN=local` and
   `-mod=readonly`, so a module or toolchain download fails the build. The
   build containers themselves are not network-isolated.
2. **Reproducible builds.** CI builds every image twice from the committed
   lockfile and fails if the two builds differ.
3. **Signing.** Every published image is cosign keyless-signed (Sigstore via
   GitHub OIDC) and carries SLSA Build Level 3 provenance and an SBOM
   attestation. Provenance is generated by GitHub (`actions/attest`) in a job
   separate from the build; the build job holds no signing credentials.
4. **SBOMs.** Every published image carries an SPDX SBOM as a signed
   attestation, bound to its digest.
5. **Vulnerability scanning.** Every image, on every platform it ships for,
   is scanned with Trivy and Grype before publication. A critical finding
   from either scanner, or a finding on CISA's Known Exploited
   Vulnerabilities list at any severity (Grype), fails the release before
   anything is pushed.

## 4. Patch cadence and release records

1. **Rebuild cadence.** A scheduled workflow (`temper-relock`) relocks every
   image against the newest Wolfi packages and opens a pull request with
   the changes. Merging it and pushing a date tag releases the rebuilt
   images.
2. **Release records.** Every release writes a signed manifest, attached to
   the GitHub release, that records the git commit, the signing mode, the
   scanner database freshness and, per image, the digest and scan results.
   Each image's provenance binds it to the source commit, which pins the
   lockfiles. These records are the evidence trail for §1.7.

## 5. Verification (CI gates)

| Requirement | Gate |
|---|---|
| Nonroot UID, no setuid, no package manager, shell only in the shell tier | `scripts/check-policy.sh` inspects every built image; any violation fails the build |
| Read-only rootfs, dropped capabilities | Runtime requirements for deployments; apko config review only, not checked in CI |
| Pinned packages | Images build from the committed lockfiles; CI re-locks and reports drift as a warning |
| Reproducible builds | CI builds every image twice and fails if the builds differ |
| Vulnerability scan | Trivy + Grype before publish; a critical or known-exploited finding fails the release |
| Signing + attestations | The release job verifies every image's signature, SLSA provenance and SBOM attestation with `scripts/verify-build.sh`, as a consumer would; any failure fails the release |
| Immutable tags | The release refuses to push a date tag that already exists, and a re-run only confirms tags already on the release's digest |
| Gated `latest` | The release job moves `latest` after verifying every image, only if the release is the newest; the manifest records the outcome |

## 6. Exceptions

Exceptions require a documented justification in the affected image's
directory (e.g. `images/<name>/README.md`) and must be time-boxed. The default
is fail-closed: without a documented exception, the requirement applies.
