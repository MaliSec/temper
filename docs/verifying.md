# Verifying a Temper image

How to check a published Temper image yourself. Everything here uses public
material: the image reference, the registry, the public Sigstore
transparency log and the release manifest. No Temper key or secret is
needed. The attestation checks use the GitHub CLI (`gh`), which needs a
GitHub login (any account; `gh auth login`) to read attestations; the
signature and manifest checks need no account.

## How releases are signed

Releases are signed **keyless**. There is no project signing key.

When the release workflow runs, GitHub gives it a short-lived token that
states which workflow it is, in which repository, at which tag. The Sigstore
certificate authority exchanges that token for a certificate, valid for a few
minutes, that binds a throwaway key to that workflow identity. The signature
and certificate are recorded in the public transparency log, and the key is
discarded.

The signing identity is the reusable workflow
`.github/workflows/temper-release-build.yml`, which `temper-release.yml`
calls when a date tag is pushed:

| | Value |
|---|---|
| Signer identity | `https://github.com/MaliSec/temper/.github/workflows/temper-release-build.yml@refs/tags/<tag>` |
| Source repository | `MaliSec/temper` |
| Token issuer | `https://token.actions.githubusercontent.com` |

Check the source repository as well as the identity. The workflow is
public and reusable, and the identity names the workflow that ran, not
the repository that called it: another repository calling it at one of
Temper's tags gets a certificate with the same identity and its own
source repository. The release jobs refuse to run outside MaliSec/temper,
but releases cut before that check carry no such guard. A signature from
any other repository, workflow or person does not verify against both.

## SLSA Build Level 3

The release workflow separates building from signing:

- The **build** job builds, policy-checks, scans and pushes the images. It
  has no permission to request a token, so no build step can sign anything.
  Each image is scanned per platform before anything is pushed.
- The **attest** job signs each image index and each platform manifest, and
  attests SLSA v1 provenance
  generated by GitHub (`actions/attest`) from the workflow run itself, not
  from anything the build wrote. It runs no build steps.
- The **release** job verifies every image the way this page describes,
  then signs the release manifest and publishes the GitHub release.

Builds run on GitHub-hosted runners, and verification rejects attestations
made on self-hosted runners.

## What a published image carries

Each image is a multi-arch index for `linux/amd64` and `linux/arm64`. Tags
point at the index; each platform has its own manifest digest.

- A **cosign signature** from the release workflow identity above, on the
  index and on each platform manifest.
- A **SLSA v1 provenance attestation**, generated by GitHub, binding each
  of those digests to the repository, the workflow and the source commit.
  The commit pins the apko lockfiles the image was built from.
- An **SPDX SBOM attestation** per platform manifest, listing every package
  in that platform's image.
- An entry in the **release manifest** for its date tag. The manifest lists
  each image's index digest, its platform digests, and the scan summary per
  platform recorded when the release was cut.

`verify-build.sh` given an index digest verifies the index and then every
platform manifest in it. Pin the index digest (what `docker pull` and tags
resolve to) unless you deploy a single platform deliberately.

Both attestations are stored in the registry next to the image and are
signed by the same workflow identity.

## Automated verification

```sh
./scripts/verify-build.sh ghcr.io/malisec/temper/<name>@sha256:<digest>
```

To resolve a release tag to its digest first, and cross-check the digest
against the release manifest you downloaded (`--date` takes the date, or
`<line>-<date>` such as `24-2026.11.19`; floating tags like `latest` and
`24` are refused):

```sh
REGISTRY=ghcr.io IMAGE_ORG=malisec ./scripts/verify-build.sh temper/<name> \
  --date 2026.11.19 --manifest temper-2026.11.19.manifest.yaml
```

Run it from a checkout of the release tag, so the provenance is checked
against that commit (or set `TEMPER_REV=<commit>`).

The script fails closed. A signature from the wrong identity, an
attestation that is missing or not signed by the release workflow,
provenance from a self-hosted runner or for another commit, or a digest
missing from the supplied manifest all exit 1. If you supply no manifest,
the script says the cross-check was skipped; it does not report it as
passed.

## Manual verification

Pin the signer to the release you consumed. For release `2026.11.19` the
identity is
`^https://github\.com/MaliSec/temper/\.github/workflows/temper-release-build\.yml@refs/tags/2026\.11\.19$`
(below, `$ID`). Any date-tag identity proves only that some release signed
the digest; the exact one proves it was this release.

Signature:

```sh
cosign verify \
  --certificate-identity-regexp "$ID" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-github-workflow-repository MaliSec/temper \
  ghcr.io/malisec/temper/<name>@sha256:<digest>
```

Provenance, bound to the commit you expect:

```sh
gh attestation verify oci://ghcr.io/malisec/temper/<name>@sha256:<digest> \
  --bundle-from-oci --repo MaliSec/temper \
  --cert-identity-regex "$ID" --cert-oidc-issuer https://token.actions.githubusercontent.com \
  --deny-self-hosted-runners --source-digest <commit>
```

SBOM attestation:

```sh
gh attestation verify oci://ghcr.io/malisec/temper/<name>@sha256:<digest> \
  --bundle-from-oci --repo MaliSec/temper \
  --cert-identity-regex "$ID" --cert-oidc-issuer https://token.actions.githubusercontent.com \
  --deny-self-hosted-runners --predicate-type https://spdx.dev/Document/v2.3
```

Add `--format json` to either to read the attestation.

Digest-to-tag binding. Download the manifest and its bundle from the
release for the date tag you consumed, verify the manifest's signature, and
confirm the index digest you pin is listed in it. The manifest is the record
of what was cut, and the cross-check that the tag you pulled is the build
the pipeline signed:

```sh
gh release download <date tag> --repo MaliSec/temper \
  --pattern 'temper-<date tag>.manifest.yaml*'
cosign verify-blob --bundle temper-<date tag>.manifest.yaml.sigstore.json \
  --certificate-identity-regexp "$ID" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-github-workflow-repository MaliSec/temper \
  temper-<date tag>.manifest.yaml
grep -F 'digest: "sha256:<digest>"' temper-<date tag>.manifest.yaml
```

`verify-build.sh --date <tag> --manifest <file>` does all of this.

## Scan findings

Each release also attaches `temper-<release>.scans.json`: every finding
both scanners reported at release time, per image and platform, with the
package, severity and fix state. The manifest counts them (`vulns_at_cut`,
`vulns_trivy_at_cut`) and records the file's sha256 (`scans_sha256`), so
the manifest's signature covers it:

```sh
gh release download <date tag> --repo MaliSec/temper \
  --pattern 'temper-<date tag>.scans.json'
grep -F "scans_sha256: \"$(sha256sum temper-<date tag>.scans.json | cut -d' ' -f1)\"" \
  temper-<date tag>.manifest.yaml
```

The findings are as of the release; scanner databases change daily.

## VEX statements

Each release also attaches `temper-<release>.vex.json`: the project's
[OpenVEX](https://openvex.dev) statements at release time (from `vex/` in
this repository), saying for a finding whether the image is affected and
why. A finding in the scans file that a statement covers carries its
status as `vex`. The manifest records the file's sha256 (`vex_sha256`):

```sh
gh release download <date tag> --repo MaliSec/temper \
  --pattern 'temper-<date tag>.vex.json'
grep -F "vex_sha256: \"$(sha256sum temper-<date tag>.vex.json | cut -d' ' -f1)\"" \
  temper-<date tag>.manifest.yaml
grype ghcr.io/malisec/temper/<image>@sha256:<digest> --vex temper-<date tag>.vex.json
```

A statement made after a release is not in that release's file. The
current statements are in `vex/` on main, and
[trust.malisec.dev](https://trust.malisec.dev) applies them to every
release, naming the commit they come from. Grype takes those files too,
with one `--vex` per file.

Statements change what is reported, not what the release gate blocks: the
gate runs on the scanners' own findings.

## The gofips evidence bundle

Each release attaches `gofips-evidence-<release>.tar.gz`: the gofips
provider's test logs for that release, natively on amd64 and arm64, most
of them against the `gofips.so` the `-fips` images ship. Its SLSA provenance
attestation names the release workflow and commit, like the images':

```sh
gh release download <release> --repo MaliSec/temper --pattern 'gofips-evidence-*'
gh attestation verify gofips-evidence-<release>.tar.gz --repo MaliSec/temper \
  --cert-identity 'https://github.com/MaliSec/temper/.github/workflows/temper-release-build.yml@refs/tags/<release>' \
  --source-ref refs/tags/<release>
```

What it contains: `providers/gofips/docs/audit/10-evidence-manifest.md`.

## Trust anchors and their limits

- The **workflow identity and source repository** are the root of trust.
  You are trusting that only a run of this repository's release workflow,
  started in this repository, can obtain a certificate naming both, which
  rests on GitHub's token service and the Sigstore certificate authority
  and log. The identity alone is not enough: see the signer table above.
- The identity names the workflow, not who pushed the tag. Any date tag
  that runs the release workflow signs with it. The workflow refuses a tag
  whose commit is not on `main`, and a repository tag ruleset limits who
  can create date tags.
- Verification needs to reach the **transparency log**.
- `latest` and line tags (`node:24`) are never verification anchors. Pin a
  digest.

## What verification does not cover

- It cannot detect a compromised release workflow or repository: a change
  merged into the release workflow signs with the same identity. Review of
  changes to `.github/workflows/` is what guards that. If you suspect a
  compromise, follow [SECURITY.md](../SECURITY.md).
- Scan results are a snapshot from the day the release was cut. Re-scan
  images you keep for long.

## Private forks

A fork without access to this identity can cut its own images in key mode
(`COSIGN_PRIVATE_KEY=... ./scripts/cut-registry.sh`) and verify them with
`COSIGN_KEY=<public key> ./scripts/verify-build.sh ...`. Key-mode images
carry a signature and an SBOM attestation but no SLSA provenance. They are
the fork's, not this project's, and the manifest records `signing: "key"`.
